# Storybook 화면 검토 안내

Storybook은 개발·화면 검토용 도구입니다. OkHub 로컬 앱을 사용하거나 [사용 가이드](../user-guide.md)를 읽기 위해 실행할 필요는 없습니다. Storybook 서버를 제품 서비스로 배포하거나 운영하는 것을 전제로 하지 않습니다.

## 실행

저장소 루트에서 다음 명령을 실행합니다.

```sh
pnpm storybook
```

현재 패키지 스크립트의 기본 포트는 6006입니다. 다른 포트로 실행했다면 터미널에 표시되는 주소를 사용하세요.

[문서 사용 흐름 열기 — 기본 포트](http://localhost:6006/?path=/story/pages-documentsflow--default)

6007 포트에서 화면을 검토하고 있다면 같은 경로를 해당 주소에서 여세요. 실행 중인 Storybook이 없으면 이 링크는 열리지 않습니다.

## 문서 흐름 검토 순서

1. `사용 흐름 / 문서 작성·검토·발행 / 문서 사용 흐름`을 엽니다.
2. 목록에서 `지도 검색 API 계약`을 열고 확정본을 확인합니다.
3. `리뷰 보기`에서 제안 문서와 변경 비교를 확인하고 리뷰 패널을 엽니다.
4. 요청 메모와 리뷰 기록을 읽고 의견·승인·수정 요청을 제출합니다.
5. 같은 문서로 돌아와 편집·발행 확인 화면을 확인합니다.
6. 목록으로 돌아와 새 문서 작성과 초안 복구 흐름을 확인합니다.

기본 스토리에서는 동작을 자동 재생하지 않습니다. 작은 상태 차이는 Controls로 확인하며, 자동 동작 검증은 별도 테스트 스토리에서 수행합니다.

## 카탈로그 구성과 재사용 범위

### 공용 프레임 검토

`UI 컴포넌트 / 패턴 / 앱 프레임 시안 / 공용 프레임`에서 상단 워크스페이스 바와 펼친 탐색·아이콘 레일·모바일 오버레이를 검토합니다. 기존 링크 형식의 스토리 ID는 `patterns-app-frame-preview--default`입니다. Controls의 `화면`으로 홈·문서 목록·상세·편집·리뷰를 선택하고, `데스크톱 최초 접힘`으로 시작 상태를 바꿀 수 있습니다. 사이드바 하단 계정은 인증 provider의 같은 사용자 정보를 사용하며 펼침·접힘·모바일에서 유지합니다.

이 프레임은 시각 검토 승인되었으며 Storybook 전용으로 유지합니다. 실제 AppShell·AppSidebar·운영 라우팅에는 연결하지 않습니다. 본문 컴포넌트는 재사용하며, 편집 내용과 탐색 접힘 상태는 시안 내부에서 유지합니다. 실제 문서·Git·GitHub에는 전송하지 않습니다.

`화면 / 홈 / 내 작업` (`pages-homepage--default`)은 승인된 프레임을 사용합니다. `홈 목록 상태` Controls에서 정상·빈 목록·로딩·조회 실패·오래된 캐시를 비교합니다. 리뷰 항목은 기존 문서 리뷰 화면으로 이동하고, 담당 Issue는 예시 GitHub URL을 새 탭으로 엽니다. 예시 저장소는 실서비스 연결을 의미하지 않습니다. 기본 스토리에는 자동 동작이 없고 별도 숨김 테스트에서 진입을 검증합니다. 실제 HomePage의 기본 데이터는 미연결 상태이며 가짜 항목은 fixtures에서만 공급합니다. 프로젝트 요약의 실제 GitHub 조회와 MCP 연결은 후속 범위입니다.

홈의 제목은 `내 작업`이며, 데이터 미연결 상태는 간결한 안내로 표시합니다. 두 목록이 최신 조회 기준으로 비어 있으면 `문서 둘러보기`로 기존 Documents 목록을 열 수 있습니다. 오래된 캐시에는 이 빈 목록 안내를 표시하지 않습니다. 리뷰와 Issue는 행 전체로 진입하며 별도 GitHub 이동 문구는 표시하지 않습니다. `홈 항목 수`를 `항목 많음`으로 바꾸면 리뷰 요청 시각 오름차순·Issue 마감일 오름차순과 목록별 5개 페이지 전환을 직접 확인할 수 있습니다. `requestedAt`·`dueDate`가 없거나 유효하지 않은 항목은 마지막에 두며 `updatedAt`으로 대체하지 않습니다. 마감일은 연결된 GitHub Project의 명시적인 날짜 필드 매핑이 필요하고 실제 조회·필드 설정은 후속 구현입니다. 리뷰는 요청 후 경과 시간, Issue는 달력 날짜를 표시합니다. 마지막 페이지에서도 목록 공간을 유지하며, 처음부터 5개 이하인 목록은 내용 높이만 사용합니다.

홈의 조합·정렬은 `HomeTasks`, 목록 상태·페이지·높이 유지는 `HomeTaskPanel`, 리뷰/Issue 항목은 `HomeTaskRows`로 분리합니다. `TaskTime`은 짧은 상대 시간과 정확한 원본 시각 표시를 담당하며, 캐시 동기화 안내에는 절대 시각을 사용합니다.

홈 리뷰·Issue 행은 `Tooltip`의 선택형 `followCursor`를 사용합니다. 마우스에서는 커서 근처와 화면 경계를 기준으로 배치하고, 키보드 포커스에서는 기존 트리거 기준 배치를 사용합니다. 공용 아이콘 tooltip에는 이 옵션을 적용하지 않습니다. 리뷰 시간은 `요청` 접두사 없이 경과 시간만 표시하며 요청자 정보는 유지합니다.

상단 `HomeInsights`는 대표 프로젝트 전체의 규칙 기반 `프로젝트 요약`과 우측 항목 패널을 제공합니다. 카드의 화살표와 전체 클릭 영역으로 진입하며 별도 `항목 보기` 문구는 표시하지 않습니다. 데스크톱에서는 본문 옆에서 너비를 조절하고, 1024px 미만에서는 우측 오버레이로 엽니다. 패널에는 항목 제목·출처·짧은 상대 시간을 표시하고, 계산 설명·정상 결과의 기준 시각은 데이터에만 유지합니다. 오래된 결과의 경고와 기준 시각은 표시합니다. 인삿말은 유지하며 오늘 날짜는 제거합니다. `분석 상태` Controls로 정상·해당 항목 없음·미연결·로딩·실패·오래된 캐시를 비교하며, 개인 작업 목록 Controls와 독립적입니다. `analyzeHomeProject`는 완전한 조회 스냅샷에서 72시간 이상 리뷰 요청 대기, 168시간 이상 업데이트 없는 진행 Issue, 직전 168시간의 PR 병합·Issue 종료를 계산합니다. 시각이 없거나 불완전한 조회는 0건으로 표시하지 않습니다. 진행 중 Issue 집합은 명시적인 Project 상태 매핑이 필요합니다. 실제 GitHub 조회·대표 프로젝트 설정·MCP 연결은 후속 구현입니다. Storybook은 고정된 예시 원본과 기준 시각을 사용합니다.

홈은 분석 요약 아래에 리뷰·Issue 두 목록만 배치합니다. 본문 컨테이너가 640px 이상이면 2열, 그 미만이면 1열입니다. 독립된 최근 활동 목록은 표시하지 않습니다. 카드 자체 폭이 420px 이하면 리뷰는 제목·요청 후 경과 시간, Issue는 제목·상태·마감일만 표시합니다. 별도 `GitHub에서 열기` 문구는 표시하지 않으며 행의 기존 이동 동작은 유지합니다. 페이지 높이는 실제 항목 아래 빈 공간으로 유지하고, 빈 행은 사용하지 않습니다.

`운영체제` Controls에서 macOS·Windows를 선택합니다. 실제 OS 자동 감지가 아니라 시각 비교용 선택이며, 창 제어 예시는 모양만 제공하고 버튼이 아닙니다. macOS는 창 제어를 왼쪽에, Windows는 오른쪽에 표시합니다. 펼친 상태에서는 상단 구분선과 사이드바 경계를 맞춥니다. 문서 열람·편집은 최대 1180px의 같은 중앙 컨테이너를 사용하므로 넓은 화면에서 제목을 상단 폴더 아이콘에 억지로 맞추지 않습니다. 접힌 상태는 상단 버튼의 겹침을 막는 최소 폭을 유지합니다. 뒤로·앞으로는 시안 내부의 화면·문서 버전 방문 기록을 이동합니다. 과거 위치에서 새 메뉴를 선택하면 앞으로 이동할 기록은 지워지며, 편집 내용은 보존합니다. 모바일에서는 탐색 토글과 이름만 표시합니다.

### 통합 기준과 남은 정합성 항목

전체 사용자 이동의 현재 검토 기준은 `화면 / 홈`, `사용 흐름 / 문서 작성·검토·발행`과 `앱 프레임 시안`입니다. 단독 문서·설정·프로젝트 스토리 일부는 기존 `PageStoryFrame` 또는 본문만 사용하며, 아직 모든 화면 스토리가 승인된 탐색 프레임으로 통합된 것은 아닙니다. 상태 단위 컴포넌트 검증과 전체 흐름 승인을 구분합니다.

현재 확인된 후속 정합성 항목은 다음과 같습니다. 자동 상호작용·접근성 테스트가 통과하더라도 이 항목의 의미적 일치까지 보장하지는 않습니다.

- `AppFramePreview`의 문서 트리는 고정 카탈로그이므로 사용 흐름에서 새로 만든 문서나 수정한 제목이 즉시 반영되지 않습니다. 목록·트리의 카탈로그 동기화가 필요합니다.
- 홈은 승인된 상태 색상을 사용하지만 기존 `ProjectPage` 빈 보드의 In progress·In review 색상은 이전 배치입니다. 프로젝트 화면 디자인에서 같은 상태 표시 정책으로 정리해야 합니다.
- 일부 단독 편집·발행 스토리는 별도 시뮬레이터와 이전 프레임을 유지합니다. 통합 문서 흐름과 공통 기능을 재사용하도록 정리하는 작업이 남아 있습니다.

검토 기준은 1440px·1024px·390px입니다. 데스크톱 메뉴 접기와 활성 메뉴, Documents 트리, 편집 종료→버전 선택→제목→편집기 순서, 리뷰 패널과 문서의 독립 스크롤을 확인합니다. 모바일에서는 Escape·바깥 클릭으로 취소하면 토글로, 메뉴를 선택하면 본문으로 포커스가 이동하는지 확인합니다. 시각 승인과 실제 앱 연결 완료를 구분합니다.

공용 CodeMirror 편집기는 코드 입력란과 별도로 이름이 있는 가로 스크롤 영역에 Tab으로 접근할 수 있습니다. `code-editor-accessibility.spec.ts`는 발행 흐름·프레임 편집 화면의 390px·1024px·1440px에서 실제 Tab 이동·방향키 스크롤·코드 입력과 axe 접근성을 검사합니다. Storybook의 코드 스크롤 테스트도 포커스 순서를 검증합니다.

홈 개인 목록과 프로젝트 요약은 `home-tasks.ts`의 공통 예시 스냅샷을 사용합니다. 같은 PR·Issue의 식별자·제목·시각·상태는 공유하며, 진행 중 Issue는 예시에 명시한 Project 상태 ID 매핑으로 선택합니다. `few`는 짧은 개인 목록을 미리 보는 부분집합이며 요약은 페이지네이션이나 개인 목록 길이에 관계없이 전체 프로젝트 예시를 계산합니다. 현재 전체 예시는 리뷰 대기 6건·업데이트 없는 진행 작업 2건·최근 병합 및 종료 3건입니다. 조회 상태 Controls는 서로 독립적인 실패 상황을 검토하기 위해 유지합니다.

- `기초 스타일`: 색상, 타이포그래피, 간격·모션.
- `UI 컴포넌트`: 공통 UI 부품과 조합 패턴.
- `문서 컴포넌트`: 문서 트리, 검색, Markdown 등 문서 전용 부품.
- `화면`: 시작·연결, 홈, 문서, 프로젝트, 설정. 문서 화면은 목록·상세·새 문서·작성 및 편집·리뷰로 묶습니다.
- `사용 흐름`: 여러 화면 사이의 진입·작업·복귀를 확인합니다.

메뉴 제목과 별개로 기존 스토리 ID는 유지하므로 기존 링크와 테스트 URL을 계속 사용할 수 있습니다.

목록·새 문서 화면은 실제 `DocumentsPage`, 상세는 `DocumentReader`, 편집은 `DocumentDraftEditor`를 재사용합니다. 연결·홈·프로젝트·설정도 실제 화면 컴포넌트를 사용합니다. 예시 데이터와 가짜 외부 의존성은 decorators와 fixtures에서 공급합니다.

리뷰의 `DocumentReviewPreview`와 통합 여정의 `DocumentsFlowPreview`는 아직 Storybook 전용입니다. 통합 여정은 실제 문서 컴포넌트를 조합하지만 발행·리뷰 결과와 화면 전환을 메모리에서 모사합니다. 실제 리뷰 기능 연결 시 리뷰 표시 UI를 공용 화면으로 추출하고 GitHub 데이터·전송 어댑터와 분리해야 합니다. 현재 카탈로그에 리뷰 화면이 있다는 사실이 앱의 리뷰 기능 구현 완료를 의미하지는 않습니다.

## Controls와 예시 데이터

`reviewState`는 예시 문서의 최초 PR 상태를 바꿉니다. 값을 바꾸면 흐름을 처음부터 시작합니다. 개별 편집·리뷰 스토리에서는 조회 실패, 권한과 제출 실패 등 해당 화면의 조건도 변경할 수 있습니다.

예시 문서의 입력과 발행·리뷰 결과는 메모리 안에서만 처리합니다. 실제 문서 파일, Git 커밋 또는 GitHub PR을 변경하지 않으며, 새로고침하면 작업 예시는 초기화됩니다. 패널 너비처럼 기기에 저장하는 UI 설정은 별개입니다.

이 예시를 일반 사용자의 실제 작업 공간이나 데이터 보관 수단으로 사용하지 마세요.

## 실제 구현 세션 인계

- 기준 브랜치: `feat/design-system-rollout`. 시작 전 작업 트리의 기존 미커밋 변경을 확인하고 보존합니다.
- 화면·동작 기준: `화면 / 문서`와 `사용 흐름 / 문서 작성·검토·발행`. 승인된 제품 정책은 `docs/product/screens.md`, `docs/product/use-cases.md`가 기준입니다.
