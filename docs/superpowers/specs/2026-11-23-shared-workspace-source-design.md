# 기준 저장소를 원본으로 사용하는 Workspace

## 합의한 목적

팀은 제품 코드 수정이나 fork 없이 기준 저장소를 등록한다. 기본 브랜치의 `.okf/workspace.yml`이 workspace UUID·이름·문서 저장소·코드 저장소·GitHub Projects의 원본이다. 앱과 외부 MCP는 같은 해석기를 사용한다. 기준 저장소가 문서 저장소일 필요는 없다.

## 현재 구조와 변경 경계

- `settings/model.rs::HubWorkspace`는 로컬에 이름·문서 저장소·Project를 저장한다.
- `settings/service.rs`는 Project ID 및 `repo:` ID로 항목을 만들고 이전 설정도 읽는다.
- `automation/mcp_workspace.rs`는 로컬 목록을 읽고, 로컬 clone이 없을 때 문서 저장소의 원격 YAML을 보강한다. 로컬 clone이 있거나 `launch:` 대상이면 원격 보강을 건너뛴다.
- YAML의 `workspace.id`는 이미 UUID이다. `documents`에는 roots만 있고 저장소 명시는 없다.
- 등록 UI는 Project/문서 저장소 연결 중심이며 공유 정의의 미리보기·확인 단계는 없다.

## 설계 선택

로컬 원본 유지, 원격 보강만 확대, 공유 원본과 로컬 등록 상태 분리 중 마지막 방식을 사용한다. 기존 hydration의 Git 조회·검증을 공용 resolver로 옮기고 앱과 MCP가 재사용한다. 자동 동기화로 로컬 연결을 덮어쓰는 방식은 사용하지 않는다.

아래 방향으로 구현한다. 실제 팀 설정 변경과 외부 쓰기는 별도 승인을 따른다.

- 기존 schema_version 1은 읽기 호환을 유지한다. `documents.repository: {id, full_name}`을 선택 필드로 추가한다. 새 등록에서 누락되면 기준 저장소를 문서 저장소 후보로 명시해 확인받는다. 기존 YAML은 자동 수정하지 않는다.
- 코드 저장소는 기존 `repositories`를 사용한다. `roles: [frontend, backend]`를 선택 필드로 추가해 하나의 저장소가 양쪽 역할을 가질 수 있게 한다. 누락 시 역할 미지정을 표시하고 이름으로 추측하지 않는다.
- 새 로컬 등록 레코드는 기준 저장소의 불변 GitHub ID·현재 full_name·YAML UUID·승인한 연결 fingerprint·legacy 별칭만 가진다. 공유 이름/대상은 resolver 결과 또는 출처가 표시된 캐시로 제공한다.
- 로컬 clone 경로·현재 선택·개인 인증·캐시는 개인 상태이다. 캐시에 정의 사본을 보관할 수 있으나 공유 원본으로 취급하지 않는다.
- 출처는 기준 저장소 ID, 기본 브랜치, 고정 commit, 설정 경로, fingerprint와 조회 시각을 포함한다. 캐시 응답에는 stale 표시와 실패 이유를 붙인다.
- 등록은 조회 → 검증/대상 미리보기 → 사용자 확인 → 같은 commit/연결 내용 재검사 → 로컬 저장 순서이다. 등록만으로 clone·GitHub 변경·대상 권한 부여를 하지 않는다.
- 같은 UUID를 다른 저장소가 선언하면 source conflict로 막는다. fork에는 원래 팀 대상이 남아 있음을 알리고 자동 등록/쓰기를 하지 않는다. 동일 조직 밖 대상이라는 이유만으로 금지하지는 않으며 실제 대상을 확인받는다.
- 연결 대상 변경은 재확인 전까지 쓰기 차단한다. 이름 변경만으로 UUID를 바꾸지 않는다. 원격 최신 확인 실패 시 캐시는 조회 참고용이고 쓰기에는 사용하지 않는다.

## 초기 설정과 등록 수명주기

1. 기준 저장소 주소를 입력한다. 저장소 신원과 기본 브랜치를 확인하고 `.okf/workspace.yml`을 조회한다.
2. 파일이 있으면 형식을 검증하고 연결 대상을 미리 보여준다. 형식 오류는 필드 위치·이유·수정 방법을 표시하며 자동 보정하지 않는다.
3. 저장소와 고정 SHA의 트리를 정상 조회해 파일 부재를 확인한 경우에만 `설정 파일 없음`으로 안내한다. 404의 권한 은폐 가능성, 인증·접근·네트워크 오류를 파일 부재와 혼동하지 않는다.
4. 파일이 없으면 `다른 저장소 선택` 또는 `설정 파일 만들기`를 제공한다. 이름·문서 저장소·선택적 코드 저장소·선택적 Projects를 입력해 UUID가 포함된 YAML 초안을 생성한다. 작성 중 취소하면 등록·원격 변경이 없다.
5. 초안 다운로드/복사만으로 GitHub에 쓰지 않는다. 사용자가 원격 반영을 요청하고 파일·브랜치·대상·내용을 확인한 뒤에만 브랜치와 PR을 만든다. 기본 브랜치 직접 반영·자동 병합은 하지 않는다.
6. PR 생성 실패·부분 성공은 구분하고 이미 만든 브랜치/PR을 안내한다. 안정적인 요청 ID로 재시도하며 중복 PR을 만들지 않는다. 병합 대기 상태는 workspace 등록 완료와 다르다. 닫힌 미병합 PR은 설정이 반영된 것으로 보지 않는다.
7. 병합 후 명시적 새로고침/재확인으로 기본 브랜치의 YAML을 다시 검증하고 최종 등록 확인을 받는다. PR을 기다리는 백그라운드 자동 등록은 하지 않는다. 다른 사람이 만든 PR로 설정이 반영되어도 같은 확인 흐름을 사용한다.
8. 기본 브랜치가 없는 빈 저장소는 파일 부재와 구분한다. 초안은 만들 수 있으나 PR 생성은 막고 먼저 저장소 초기화가 필요함을 안내한다. 초기 commit·저장소 생성은 자동 수행하지 않는다.

## 문서 전용·일부 접근 실패·Project 선택

- Projects가 없어도 문서 전용 workspace를 등록한다. 보드와 보드 쓰기 기능만 비활성화하고 Project 연결 안내를 제공한다. 코드 저장소 역시 없어도 된다.
- 기준 저장소의 정의를 읽고 검증할 수 있지만 일부 대상에 접근하지 못하면 정상인 대상을 사용할 수 있다. 대상마다 접근 결과와 오류를 표시하며, 읽지 못한 항목을 빈 목록으로 표현하지 않는다.
- 불완전한 근거가 필요한 쓰기는 차단한다. 관련 없는 다른 저장소의 접근 실패가 모든 기능을 일괄 중단시키지는 않는다. 기준 정의 자체를 최신으로 확인할 수 없으면 모든 공유 대상 쓰기를 차단한다.
- YAML의 기본 Project를 팀 기본값으로 사용한다. 2026-11-25 사용자 결정에 따라 개인별 기본 보드 지정·저장 기능은 이번 범위에서 제외한다. Settings의 Workspaces 상세에는 현재 팀 기본 보드를 `기본`으로 표시한다. 다른 보드의 기본 변경과 보드 추가·제거는 하나의 팀 설정 변경안으로 모아 PR로 제출한다. 개인 선택 버튼은 제공하지 않는다. 실제 작업 보드 선택은 Project 화면의 작업 맥락으로 분리한다. 기존 개인 설정 데이터는 이 결정만으로 삭제하거나 변경하지 않는다.
- 후속 운영 전환 시 MCP는 서버 시작 시 YAML 팀 기본값 → 유일한 Project 순서로 기본 대상을 고정하며, 개인 기본 보드 선호를 새로 도입하거나 기본 대상 결정에 사용하지 않는다. 기존 운영 MCP 코드는 이번 시안 수정에서 변경하지 않는다. 여러 개이고 기본값이 없으면 projectId를 요청한다. 호출별 projectId는 다른 호출의 기본 대상을 변경하지 않는다. 앱과 MCP의 연결 정의는 같고 현재 선택은 세션별임을 구분한다.

## 변경·복구·등록 해제

- 연결 대상 변경은 이전/새 대상을 비교하는 화면에서 재확인한다. 취소하면 승인된 범위는 보존하지만 미확인 새 대상으로 쓰지 않는다.
- 저장소 삭제·이전·권한 상실·네트워크 오류는 구분 가능한 범위 내에서 표시한다. GitHub가 404로 접근 제한을 숨길 수 있으므로 삭제라고 단정하지 않는다. 재시도·다른 기준 저장소로 재연결·이 기기에서 등록 해제를 제공한다.
- 같은 source와 UUID를 다시 등록하면 기존 항목으로 안내한다. 다른 source의 같은 UUID는 자동 병합하지 않는다. source 교체는 기존/새 저장소와 대상 비교 후 명시적으로 승인받고 별칭을 보존한다.
- 등록 해제는 이 기기의 registry·선택·개인 Project 선호·캐시 참조만 제거한다. GitHub 저장소·Project·Issue·PR, 로컬 clone과 수정 파일, 작업 journal은 삭제하지 않는다. 진행 중 쓰기는 등록 변경 재검사로 중단한다. 다른 workspace와 기존 호환 키도 해제 항목을 되살리지 않아야 한다.

## UI 문구·목록 동작 — 2026-11-25 사용자 확정

- 불필요한 설명을 기본으로 넣지 않는다. 제목·레이블·버튼·표시된 값의 반복, 구현 절차 해설은 제거한다. 필요한 설명은 제목 아래 한 문장으로 두고 상단 중복 제목·단계 표시를 사용하지 않는다.
- 저장소 선택은 목록 검색과 주소 입력을 제공한다. 작은 시안 목록은 전체를 검색하게 하고, 임의의 2개 단위 `더 불러오기`는 사용하지 않는다. 실제 대량 데이터는 API 페이지네이션을 유지하되 UI 추가 단계를 노출할지는 별도로 검토한다.
- 정상 목록의 `N개 불러옴`, 선택값 재출력, 버튼 동작을 설명하는 문장은 두지 않는다. 로딩·빈 결과·오류 및 해결 행동은 유지한다.
- 삭제 시 보존 범위, 설정 원본 변경과 GitHub 파일 수정의 차이, PR 병합 전 미반영 등 사용자의 결정에 필요한 안내만 남긴다.
- 보드 추가·제거와 팀 기본값 변경은 하나의 변경안으로 모아 한 번 검토하고 PR로 제출한다. 개인별 기본 보드가 아니다. 현재 기본은 chip, 나머지는 기본 변경 버튼을 제공하며 제출·병합 확인 전 실제 chip을 이동하지 않는다.
- 보드는 목록 안에서 편집한다. 테스트용 응답 선택은 제품 작업 화면에서 분리한다.
- 공통 기준: `docs/superpowers/plans/2026-08-20-design-system-foundation.md`의 UI 문구 원칙.

## UI/UX 변경 범위

- 연결 화면: 기준 저장소 입력 → 조회 상태 → 연결 대상 미리보기 → 등록 확인의 단계형 흐름.
- 설정 없음: YAML 작성 폼·초안 미리보기·복사/다운로드·PR 생성 확인·병합 대기 및 다시 확인 화면.
- 관리 화면: breadcrumb 아래 workspace 이름, 기준 저장소 링크·마지막 확인 시각·대상별 접근 오류를 표시한다. 새로고침은 확인 시각 옆 아이콘으로 두고, 실패 시 재시도 행동을 표시한다. 원본에 대한 반복 설명과 기술 정보는 기본 화면에서 제외한다. 연결 변경 비교는 필요 시 제공하며 재연결·해제는 제목 옆 `⋯`에 배치한다. `저장소에서 가져오기`는 목록에서만 제공한다.
- Project 표시·편집: 문서 전용 상태와 현재 팀 기본 보드를 표시한다. 팀 보드 구성·기본값 변경은 한 변경안으로 검토 후 PR을 생성하며, 병합 확인 전에는 적용하지 않는다. 개인별 기본 보드 선택은 이번 범위에서 제외한다. Project 화면의 작업 보드 전환과 설정 관리 화면은 구분한다.
- 공용 프레임·문서 작성/리뷰 본문 디자인은 이번 범위에서 재설계하지 않는다. 관련 상태·진입 버튼·안내만 변경한다. 단계 이동 시 입력 보존, 로딩/오류 재시도, 키보드·포커스·모바일 대응을 검증한다.

## 호환·이관

기존 설정을 시작 시 파괴적으로 바꾸지 않는다. 기존 연결은 legacy로 표시하고 기준 저장소 등록/전환을 확인받는다. 확인 후 UUID 기반 등록과 기존 ID 별칭을 원자적으로 저장한다. 옛 ID로의 MCP 요청은 확인된 별칭에만 매핑한다. 선택·clone·개인 설정 연결을 보존하고, 기존 실행 journal은 옮기거나 requestId 의미를 변경하지 않는다. 진행 중 쓰기는 설정 변경 시 기존 fingerprint 검사로 중단한다.

## 비목표와 권한

팀의 실제 YAML 수정, 원격 commit/PR, push, 개인 MCP 설정 변경, 인증 범위 확장은 별도 승인 대상이다. 이번 작업은 제품의 조회·검증·등록 기능과 예시 및 테스트이다. 실제 팀 설정을 제품에 하드코딩하지 않는다.
