# 화면 구성

이 문서는 합의된 전역 화면 구조와 아직 구체화 중인 화면별 책임을 정리합니다.

## 앱 수준 화면

### 최초 연결 화면

워크스페이스가 연결되지 않은 최초 실행 또는 연결 복구가 필요할 때만 표시합니다.

- GitHub 로그인
- 기존 OKF 지식 저장소 연결
- 새 OKF 지식 저장소와 `.okf/workspace.yml` 초기화
- 저장소 접근 권한과 워크스페이스 설정 검증

GitHub 인증 대기 화면은 인증 코드·복사 동작·유효 시간을 함께 보여주고, `GitHub에서 인증 계속`을 주 동작으로 제공합니다. 필수 인증의 정상 대기 상태에는 별도의 취소·재시작 버튼을 표시하지 않으며, 만료·오류 상태에서만 복구 동작을 제공합니다.

최근 워크스페이스 목록, 워크스페이스 선택과 전환 화면은 제공하지 않습니다. 연결이 완료된 뒤 앱을 다시 열면 현재 워크스페이스의 Home으로 바로 진입합니다.

저장소 선택 단계에서는 기존 저장소를 선택한 뒤 `다음`으로 로컬 연결에 진입합니다. 목록을 불러오는 동안과 선택할 저장소가 없는 상태를 구분하며, 로딩 중에는 진행을 막습니다. 새 저장소 만들기는 GitHub의 새 창에서 수행하고, 사용자는 이 화면으로 돌아와 새로고침한 뒤 저장소를 선택합니다.

로컬 연결 실패는 별도 오류 화면으로 전환하지 않고 연결 폼 안에서 복구합니다. 선택한 폴더 경로를 유지하며 경로 오류는 해당 필드에 연결하고, 작업 자체의 오류는 폼 내부 안내로 표시합니다. 경로는 직접 입력하지 않고 폴더 선택으로 변경하며 기존 복구 동작을 유지합니다.

로컬 연결 방법은 공용 Radio를 사용하는 설명형 선택 카드로 표시합니다. `이 기기의 저장소 연결`과 `새로 다운로드해서 연결` 중 하나를 선택하고, 공통 경로 필드 우측의 `폴더 선택` 또는 `변경` 버튼으로 위치를 고릅니다. 폴더 선택 자체는 연결이나 다운로드를 실행하지 않습니다. 다운로드할 최종 경로는 위치 필드 아래에 표시하며 별도 확인 카드를 추가하지 않습니다. 하단 `연결` 또는 `다운로드해서 연결` 버튼을 눌렀을 때만 검증·연결 또는 새 폴더 생성·다운로드를 실행합니다.

로그아웃 후에도 workspace 연결 설정은 로컬에 유지하지만 화면에는 workspace 이름·경로·문서를 표시하지 않습니다. 재로그인에 성공하면 저장소 접근 권한과 로컬 workspace를 검증한 뒤 Home으로 자동 복귀하며, 복원할 수 없을 때만 공개 오류 또는 기존 연결 복구 화면을 표시합니다.

### 워크스페이스 설정

- 현재 OKF 지식 저장소와 `.okf/workspace.yml`
- 백엔드·프론트엔드 코드 저장소
- GitHub 인증과 동기화
- 기본 브랜치
- 제품 구조와 문서 템플릿
- Codex/MCP 연결 안내
- 연결 오류 복구와 현재 워크스페이스 재연결

프로젝트 저장소 연결은 워크스페이스의 좌측 주 메뉴에 두지 않습니다. Settings는 현재 단일 워크스페이스의 연결을 관리하며 다른 워크스페이스로 빠르게 전환하는 선택기를 제공하지 않습니다.

## 워크스페이스 전역 구조

**상태: 합의**

```text
Home
Documents
Project
Settings
────────
Documents 트리 (Documents 경로에서 표시)
```

- `Work`는 독자적인 데이터와 행동이 없어 전역 메뉴에서 제외합니다.
- `Activity`는 Home의 타임라인으로 흡수합니다.
- `Reviews`는 독립 콘텐츠가 아니라 문서나 PR에 붙는 처리 과정이므로 전역 메뉴에서 제외합니다.
- 사용자가 확인해야 할 검토, 결정과 작업 시작 알림은 Home에서 모아 보여주고, 실제 처리는 원래 문서, Issue나 PR 문맥에서 진행합니다.
- 사이드바 상단에는 현재 프로젝트 이름을 정적인 식별 정보로 표시하며 드롭다운 화살표나 워크스페이스 선택 동작을 두지 않습니다.
- 사이드바는 회색 `canvas`, 본문은 흰색 `surface`를 사용합니다. 앱 전체 높이를 고정하고 본문과 문서 트리만 각자 스크롤하여 본문 끝의 탄성 스크롤이 사이드바를 움직이지 않게 합니다.
- Documents 홈에는 검색창 오른쪽의 `새 문서` 버튼을 유지합니다. Documents 경로에서는 문서 상세나 편집 중에도 문서 트리 상단의 Lucide `Plus` 버튼으로 새 문서를 만들 수 있고, 폴더의 `Plus`는 그 폴더를 기본 생성 위치로 사용합니다.
- 좌측 사이드바는 완전히 접을 수 있으며, 접으면 본문이 남은 폭을 사용합니다. 펼친 상태의 토글은 사이드바 최상단 오른쪽에 두고, 접힌 상태에서는 같은 기능의 버튼을 본문 왼쪽 위에 표시합니다.
- 사이드바 토글은 Lucide의 `PanelLeftClose`·`PanelLeftOpen` 계열 아이콘과 설명 tooltip을 사용하고, macOS `Command + Backslash`, Windows `Ctrl + Backslash` 단축키를 제공합니다.

### Home

앱을 열었을 때 현재 단일 워크스페이스의 프로젝트 진행 상황과 다음 행동을 보여줍니다.

- `프로젝트 진행 상황` 제목
- 제목 아래의 인사말과 오늘 날짜
- 열린 Issue, 진행 중인 Issue, 이번 주 완료 Issue 요약
- 기능별 진행률과 완료 Issue 수
- 내가 확인할 항목
  - 검토 필요
  - 결정 필요
  - 작업 시작 가능
  - 응답 필요
- 발생 시간을 포함한 최근 활동

기능 진행률은 초기에는 연결된 Issue의 `완료 수 / 전체 수`로 계산하고 퍼센트와 실제 개수를 함께 보여줍니다. 작업 크기를 반영한 가중 진행률은 초기 범위에서 제외합니다.

백엔드 API 완료처럼 누군가의 승인이 필요하지 않더라도 후속 작업자가 다음 행동을 시작해야 하는 이벤트는 `작업 시작 가능` 항목으로 표시합니다. 연결된 선행 Issue 종료나 PR 병합을 기준으로 만들며, 정확한 연결이 없으면 자동으로 추론하지 않습니다.

현재 합의한 것은 Home의 정보 구성, 표시 순서와 영역별 책임입니다. 색상, 타이포그래피, 간격, 카드 모양과 반응형 표현을 포함한 최종 시각 디자인은 별도 단계에서 확정합니다.

### Documents

- 제품 구조 탐색
- 문서 라이브러리
- 문서 편집과 렌더링
- 문서별 Git history
- 관련 분석·테스트·API·코드
- 현재 버전과 제안 버전 전환

Documents는 문서가 중심인 공간입니다. `History`는 별도 전역 메뉴가 아니라 각 문서의 커밋·변경·승인 이력을 보여주는 상세 보기입니다. 진행 중인 작업을 별도 목록으로 소유하지 않으며, 문서에서 관련 Issue나 리뷰 상태를 참조 정보로 확인할 수 있습니다.

- Documents 홈의 페이지 헤더는 제목과 설명만 둡니다. 홈은 기본 브랜치의 문서 목록을 검색·생성하는 곳이며, 목록 위에 별도의 작업 기준 선택기나 `모든 문서` 제목을 두지 않습니다.
- 열린 Draft의 `변경 작업` 전환과 실제 branch명 구분은 문서 상세·편집 화면에서만 제공합니다.
- 문서 목록 항목은 기본 상태부터 얇은 경계를 가지며, hover에서는 경계를 바꾸지 않고 배경만 살짝 강조합니다.

#### 문서 작성과 발행

- 문서 편집·열람은 동일한 H1~H6 타이포그래피를 사용합니다. 링크는 밑줄로 구분하고 저장소 이미지를 실제 자산으로 표시하며, 이미지 편집 도구와 코드 블록의 언어·복사·삭제 조작은 해당 콘텐츠 안에 배치합니다. 체크 목록과 표 셀은 키보드 조작과 접근 가능한 이름을 유지합니다.
- 기본 작성·마무리 단위는 문서 한 개입니다. 관련 문서 여러 개를 묶는 흐름은 선택 기능으로 두며, 현재 문서의 발행에 다른 초안 문서를 자동으로 포함하지 않습니다.
- 작성 내용은 로컬 초안에 자동 저장합니다. `편집 종료`나 다른 화면으로 이동하는 동작은 발행이 아니며 초안을 유지합니다.
- 편집 화면의 작업 버튼은 보조 동작인 `변경 취소`와 주요 동작인 `발행`으로 구성합니다. `변경 취소`는 기존 문서의 로컬 작성 변경만 버리고 마지막 확정본으로 복원하며, 새 문서는 아직 발행하지 않은 로컬 문서를 제거합니다. 실행 전에 대상과 결과를 확인하고 다른 문서의 초안이나 확정본은 변경하지 않습니다. 폐기한 초안은 로컬에서 7일간 복구할 수 있으며, 이미 공유한 PR은 유지합니다. PR 닫기는 별도 동작입니다.
- 변경 취소 후 기존 문서는 마지막 확정본 화면으로 돌아가고, 미발행 새 문서는 문서 목록으로 이동합니다. 완료는 `실행 취소`가 포함된 일시적 토스트로 알립니다. 토스트가 사라진 뒤에도 문서 목록의 `최근 삭제한 초안`에서 7일 이내의 로컬 변경·새 문서를 복구할 수 있습니다. 만료된 항목은 복구 목록에서 제외하며, 문서 본문에 폐기·만료 안내나 비활성 복구 버튼을 지속 표시하지 않습니다.
- `발행`은 현재 문서를 확정본에 반영하는 주요 동작입니다. 발행 전에 대상 문서와 반영 범위를 확인하며, commit·push·병합 같은 Git 단계는 내부 절차로 처리합니다. 별도 커밋 버튼과 변경사항 관리 패널을 기본 작성 흐름에 노출하지 않습니다.
- 편집기는 `문서 편집 / Markdown 원문`을 제공하고 같은 초안을 유지합니다. 발행 확인 화면은 줄 번호와 추가·삭제 표시가 있는 `원문 비교`를 기본으로 제공합니다. 넓은 화면에서는 변경 줄을 정렬한 좌우 비교, 좁은 화면에서는 삭제·추가를 이어 보여주는 통합 비교를 사용합니다. `문서 미리보기`로 전환해 렌더링 결과를 확인할 수 있습니다. 새 수정 커밋을 만드는 경우에만 `변경 설명`을 필수로 입력받아 커밋 메시지로 사용합니다. 이미 PR에 공유한 내용의 발행·재검토 요청에는 불필요한 새 커밋 메시지를 요구하지 않습니다. 병합 메시지는 수정 커밋 메시지와 구분하며 저장소가 지원하는 병합 방식에 따릅니다. 발행 실패나 취소 시 초안과 입력한 설명은 유지합니다. 선택적인 검토 요청도 같은 비교 흐름을 사용하되 마지막 동작은 확정본 반영이 아니라 PR 공유입니다.
- `발행` 확인 화면에서 `바로 발행 / 검토 요청`을 선택합니다. 편집 화면에는 별도 검토 요청 버튼을 두지 않습니다. `검토 요청`과 타인의 승인은 선택 과정입니다. 검토를 원할 때 GitHub PR로 현재 문서를 공유하되, 요청만으로 확정본이 바뀌지는 않습니다. GitHub 권한·브랜치 보호 규칙은 우회하지 않으며 직접 발행할 수 없는 경우 이유와 가능한 검토 경로를 안내합니다.
- 검토 승인은 자동 발행을 의미하지 않습니다. 승인 후에도 작성자가 명시적으로 `발행`을 눌러 확정본 반영을 시작합니다. 발행 시점에 반영 대상과 저장소의 권한·보호 규칙을 다시 검증합니다.
- 발행 완료 후 다시 편집하면 최신 확정본을 기준으로 새 로컬 초안을 시작합니다. 병합된 PR은 이전 발행 이력으로 보존하되 현재 작업의 PR·승인 상태로 이어받지 않습니다. 새 초안에서 검토 요청을 선택하면 새 PR을 생성하며, 비교 기준은 직전 확정본입니다. 열린 PR의 수정 작업은 기존 PR을 계속 갱신합니다.
- 병합하지 않고 닫힌 PR이 연결된 경우 현재 작성 내용과 비교 기준을 유지합니다. 검토 요청 화면에서 기존 PR의 종료와 새 PR 생성 사실을 안내하고, 사용자가 요청을 보내면 이전 PR을 이력으로 남긴 뒤 새 PR을 연결합니다. 이전 승인 상태를 이어받거나 기존 PR을 자동으로 다시 열지 않습니다.
- 여러 문서를 포함한 초안 branch 전체를 병합하거나 rebase하지 않습니다. 현재 문서의 변경만 발행용 branch로 분리하고, 공유 전 최신 확정본 위로 rebase합니다. 발행 후 다른 문서의 작성 내용과 기준본은 유지하며, 각 문서를 발행할 때 최신화합니다. 공유된 PR 이력의 안전한 갱신 방식과 원격 검증·충돌 처리는 별도 구현 설계로 구체화합니다.
- `검토 요청`은 PR이 없으면 현재 문서를 커밋·push한 뒤 PR을 생성하고, 이미 연결된 열린 PR이 있으면 같은 PR을 갱신합니다. 별도의 `검토 요청 업데이트`나 `수정본 보내기` 버튼을 두지 않습니다. 자동 저장만으로는 PR을 갱신하지 않습니다. 검토 대상이 바뀌면 이전 승인을 새 변경의 승인으로 간주하지 않습니다.
- 기존 PR 갱신은 해당 PR의 head branch에 현재 문서 수정본을 새 커밋으로 추가하고 push하는 동작이며, 새 PR 생성이나 description만의 수정을 뜻하지 않습니다. `변경 설명`은 이번 커밋 메시지이고 `검토 요청 메모`는 PR description입니다. 기존 PR이면 현재 원격 description을 불러와 미리 채우며, 사용자가 수정하지 않으면 원격 description을 그대로 유지합니다. 사용자가 수정한 설명을 반영하기 전에는 원격에서 다시 바뀌었는지 확인하고 타인의 변경을 조용히 덮어쓰지 않습니다.
- PR 번호와 검토 상태는 편집·열람 화면의 제목 아래 문서 정보로 표시하며 작업 버튼 영역과 분리합니다. 파일 경로 다음 줄에 PR 번호와 상태를 함께 표시하고, PR 번호는 해당 GitHub PR 페이지를 새 탭으로 여는 링크로 제공합니다. Storybook 시뮬레이션 안내는 스토리 설명에 두고 제품 화면 안에는 노출하지 않습니다.
- PR 검토 상태(대기·수정 요청·승인·발행 완료·검토 종료)와 로컬 미공유 변경 여부는 독립적으로 표시합니다. 미공유 변경이 있어도 기존 PR의 검토 상태를 대체하지 않으며, 이전 승인이 로컬 수정본의 승인임을 뜻하지 않습니다.
- `의견 남기기 / 승인 / 수정 요청`은 GitHub 리뷰의 `Comment / Approve / Request changes`에 대응합니다. 일반 댓글이나 미승인만으로 수정 요청 상태를 만들지 않습니다. 수정본 push·재검토 요청만으로 기존 수정 요청을 해제하거나 검토 대기로 덮어쓰지 않습니다. GitHub의 현재 유효한 리뷰 결과를 조회해 상태를 갱신합니다.
- 검토 상태와 발행 가능 여부는 별도로 다룹니다. 승인됐어도 필수 검사, 충돌, 권한, 필요한 승인 수·CODEOWNERS·최신 변경 승인 등의 저장소 조건이 충족되지 않으면 발행하지 않습니다. GitHub 승인이 실제 취소됐는지와 앱의 `재검토 필요` 안내를 구분합니다. 이전 버전의 승인을 현재 수정본에 재사용하지 않되, 앱이 원격 승인을 임의로 취소했다고 표시하지 않습니다.
- 필수 검사 진행 중과 실패 상태를 구분해 발행 제한을 안내합니다. 검사 상태가 바뀌어도 작성 내용, 변경 설명과 열린 확인창을 유지하며, 제한이 해제되면 사용자가 같은 확인창에서 발행을 재시도합니다. 검사 통과만으로 자동 발행하지 않습니다.
- 연결된 열린 PR에 미공유 변경이 있으면 발행 과정에서 현재 문서 수정본을 커밋·push하고 원격 병합 조건을 다시 확인합니다. 수정본 공유와 새 검토·승인의 의무 여부를 혼동하지 않으며, 저장소가 검토를 요구하지 않으면 별도 검토 요청 단계를 강제하지 않습니다. 닫히거나 병합된 PR은 자동 재사용하지 않습니다. 새 PR 생성 또는 재개는 별도 사용자 확인을 거쳐야 하며, 준비되지 않은 경로는 성공으로 가장하지 않습니다.
- 발행·PR 생성·수정본 공유의 성공은 본문을 밀어내는 지속 배너 대신 자동으로 사라지는 토스트로 알립니다. 현재 검토 상태는 문서 정보에 계속 표시하며, 실패·조치 필요·초안 복구 안내는 관련 화면에 유지합니다.
- 현재 화면 구현은 비교·설명 입력 UI까지입니다. 확정본 조회와 Git 발행·PR 전송 API가 연결되기 전에는 앱의 최종 전송을 막고 미연결 상태를 안내합니다. 로컬에 자동 저장된 내용을 확정본으로 간주하거나 성공 상태를 가정하지 않습니다. Storybook의 성공·실패 흐름은 실제 Git 전송 없는 시뮬레이션으로 구분합니다.
- 비교 방식 탭 아래에는 문서별 접기·펼치기 영역을 둡니다. 문서가 하나면 기본으로 펼치며, 접어도 제목·파일 경로·추가·삭제 수는 유지합니다. 보기 방식을 전환해도 접힘 상태와 대상 문서는 유지합니다. 여러 문서로 확장할 때도 같은 단위를 사용하되, 발행 대상 선택은 내용 접기·펼치기와 별도 동작으로 구분합니다.

#### 새 문서 생성과 로컬 Draft

- Documents 상단과 좌측 트리의 `새 문서`는 같은 생성 대화상자를 엽니다.
- 생성 대화상자는 제목, 저장 폴더와 템플릿을 보여줍니다. 파일명은 별도 입력 없이 제목으로 자동 생성하며, 공백을 하이픈으로 정규화하고 `.md`를 붙입니다. 같은 경로가 있으면 뒤에 숫자를 붙여 기존 파일을 덮어쓰지 않습니다. 제목 아래에는 `파일명은 제목으로 자동 생성되며, 중복 시 숫자가 붙습니다.`를 보조 안내로 표시합니다.
- 저장 폴더는 프로젝트 문서 폴더의 계층을 펼쳐 선택하는 드롭다운입니다. 트리의 폴더에서 시작하면 해당 폴더를 기본값으로 사용합니다.
- 저장 폴더 라벨 옆의 Lucide `FolderPlus` 버튼은 선택창 아래에 새 폴더 입력을 엽니다. 기존 경로와 새 이름을 연결하여 표시합니다. `새 폴더 이름` 줄 오른쪽 X로 입력을 취소하고, 입력창 바로 오른쪽에는 추가 버튼만 제공합니다. 별도 취소 버튼이나 하위 폴더 안내 문구는 두지 않습니다.
- `/`로 하위 경로를 입력할 수 있습니다. `/`까지 입력한 이름은 앞쪽 경로로 이동하고, 기존 폴더는 회색, 생성 예정 폴더는 teal로 구분합니다. 빈 입력에서 Backspace는 이전 이름을 다시 편집합니다. 중간 기존 폴더는 재사용하며 없는 폴더만 추가합니다.
- 경로가 입력창 폭을 넘으면 왼쪽 부분을 가리고 마지막 경로와 현재 입력을 유지합니다. 입력창 안에 가로 스크롤바를 표시하지 않습니다.
- 폴더 추가는 생성 예정 상태이며 문서 만들기 시 실제 생성합니다. 생성 예정 폴더는 추가 취소할 수 있고, 문서 생성을 취소하면 예정 폴더도 생성하지 않습니다. 기존 폴더 삭제·이동은 이 화면에 넣지 않습니다.
- 넓은 화면에서는 왼쪽에 제목·폴더·템플릿 입력을 세로로 배치하고, 오른쪽에 선택한 템플릿의 미리보기를 제공합니다. 좁은 화면에서는 미리보기를 입력 영역 아래에 배치합니다.
- 기본 템플릿의 오른쪽 미리보기는 내용이 채워진 가상 작성 예시를 보여줍니다. 예시와 생성용 템플릿은 분리하고, 예시가 생성 파일에 포함되지 않음을 안내합니다. 별도 예시가 없는 팀 템플릿은 실제 템플릿 구조를 보여줍니다.
- 템플릿은 공용 Select에서 선택하며 기본값은 `빈 문서`입니다. `기본 템플릿`과 `.okf/templates/`의 `팀 템플릿`을 구분하고, 선택한 템플릿 설명만 표시합니다. 템플릿 검색과 별도 `시작` 단계는 두지 않습니다.
- 새 문서 대화상자에는 팀 템플릿 복제·관리 기능을 넣지 않습니다. 별도 관리 진입점은 미정입니다.
- 기본 템플릿은 빈 문서, 기능 설계, 시스템·아키텍처 설계, API 계약, 기술 결정, 기술 조사, 분석·실험, 테스트 계획·결과와 장애 회고입니다.
- 새 문서 생성은 작성에 필요한 정보만 다루며, 하단에는 `취소`와 `문서 만들기`만 둡니다. 검토 대상 문서 선택과 검토 요청은 별도 흐름에서 다룹니다. 해당 흐름의 상세 설계는 미정입니다.
- 활성 Draft가 있으면 현재 변경에 문서를 추가하고, 없으면 새 Draft를 만듭니다. 생성 화면에서 내부 작업 분리 방식을 선택하게 하지 않습니다.
- 새 Draft는 앱 데이터 영역의 독립 worktree와 `draft/<login>/<change-id>-<slug>` branch를 사용합니다. worktree 절대 경로는 화면에 노출하지 않습니다.
- 생성 후 바로 편집 화면을 열며, 로컬 저장 상태와 Git commit·push 상태를 같은 의미로 표시하지 않습니다.
- 앱 재시작 시 마지막 Draft를 자동 복원하고, Documents에서 다른 Draft 또는 main으로 전환할 수 있습니다.

빈 폴더는 `.gitkeep`으로 유지하며 첫 문서가 생기면 marker를 제거합니다. 같은 경로가 있으면 자동으로 덮어쓰지 않고 대체 파일명을 확인받습니다.

문서 상세는 기본적으로 읽기 모드로 엽니다. 기본 브랜치의 확정 문서에서 `편집`을 누르면 변경 제안을 만들고, 이미 작업 브랜치나 PR 버전을 보고 있다면 해당 버전을 바로 편집합니다.

상세 화면은 다음 3개 영역을 사용합니다.

```text
문서 트리 | 읽기·리치 편집·Markdown 원문 캔버스 | 접을 수 있는 문맥 패널
```

- 본문 캔버스는 한 번에 읽기, 리치 편집 또는 원문 중 하나에 집중합니다.
- 읽기 화면의 제목·수정 정보·편집 및 더보기 동작은 왼쪽 문서 영역에 속합니다. 우측 문맥 패널은 문서 제목과 같은 상단 시작점에서 별도 열로 표시하고, 두 영역의 구분선은 제목 높이부터 이어집니다.
- 우측 문맥 패널은 `개요 / 연결 / History / 댓글` 탭으로 구성합니다.
- `개요`는 문서 속성을 먼저 보여주고 그 아래에 목차를 표시합니다.
- 읽기 화면의 본문 스크롤은 왼쪽 문서 영역 안에서 동작하며, 우측 문맥 패널은 독립된 영역으로 유지합니다. 좁은 화면에서는 문맥 패널을 본문 아래로 내리지 않고 기본 숨김으로 두며, 문서 헤더의 패널 아이콘으로 우측 overlay를 엽니다. 닫기·Escape로 닫으면 열기 아이콘으로 focus가 돌아가고, 목차를 선택하면 패널을 닫으며 해당 본문 제목으로 이동합니다. 목차는 현재 읽는 위치를 표시하되, 문서 끝의 스크롤 한계로 제목을 상단에 놓을 수 없어도 클릭한 항목의 강조를 유지하고 사용자가 다시 스크롤하면 위치 추적을 재개합니다.
- `연결`에는 관련 Issue, PR, 코드와 API를 모아 보여줍니다.
- `댓글`은 변경 제안이나 리뷰 문맥에서만 표시합니다.
- 문서 제목 아래에는 `확정본 · main`과 같이 현재 Git 버전을 보여주는 선택기를 두고, 열린 변경 제안이 있으면 선택기 옆에 개수 배지를 표시합니다.
- 마지막 수정 시각과 작성자는 제목 아래에 짧게 표시하고, 커밋별 상세 수정 이력과 diff는 우측 `History` 탭에서 확인합니다.
- 읽기 화면의 Markdown은 CommonMark와 GFM을 기준으로 제목, 목록, 표, 코드, 이미지, 각주, GitHub형 안내 블록과 안전하게 허용한 접기 영역을 렌더링합니다. 일반 본문은 타이포그래피 중심으로 표시하고, 표와 코드는 자신의 영역 안에서만 가로 스크롤합니다.
- 문서 제목과 첫 원문 H1이 같으면 제목은 한 번만 표시하며 원문의 안정적인 heading ID를 유지합니다. 목차와 본문 내부 링크는 같은 제목·절을 가리킵니다.
- 코드 블록은 언어와 복사 action을 제공하고 복사 성공을 표시합니다. 접기 영역은 마우스와 키보드로 여닫으며 task list는 읽기 전용입니다.
- 이미지는 저장소 내부 asset을 사용하고 캡션과 각주 왕복 링크를 지원합니다. 원격 이미지와 지원하지 않는 파일 링크는 설명이 있는 대체 표시를 사용하며 임의 HTML은 실행하지 않습니다.
- Mermaid는 별도 카드 없이 문서 위에 직접 표시하며, 우측 상단의 확장 버튼으로 전체 화면에서 맞춤·확대·축소·이동할 수 있습니다. 닫으면 원래 확장 버튼으로 focus를 돌려줍니다.
- 다이어그램 전체 화면은 50–300% 확대 범위, 100% 초기화와 Escape 닫기를 제공합니다. 렌더링 중이거나 잘못된 원문일 때는 확장 action을 제공하지 않고 대기·오류 상태를 표시합니다.
- 문서 오버플로 메뉴의 `보기 밀도`에서 `편안하게`와 `작게`를 전환하며 선택은 기기별 표시 밀도 설정과 동기화합니다. 화면 폭이 선택한 밀도를 자동으로 바꾸지 않습니다.

문서 제목과 Git 파일 경로는 서로 다른 값으로 다룹니다. 화면에 보이는 제목은 OKF frontmatter의 `title`이며 편집 모드에서 수정합니다. 파일명과 폴더를 바꾸는 구조 작업은 오버플로 메뉴의 `파일 경로 변경…`으로 제공하고, 영향받는 문서 링크를 확인한 뒤 변경 제안에 반영합니다. 의미가 모호한 `이름 변경` 액션은 사용하지 않습니다.

편집 헤더에는 로컬 자동 저장의 대기·진행·완료·실패 상태를 표시하고, Git 반영 완료와 구분합니다. 제목과 첫 H1이 연결된 문서는 제목을 지웠다가 다시 입력하거나 공백을 입력하는 중에도 연결을 유지합니다. 편집 툴바는 한국어로 제공하고 편집 기록·글자 서식·목록·삽입 기능을 구분합니다.

문서 헤더의 주요 작업은 텍스트 `편집` 버튼으로 노출하고, 그 옆에 Lucide `Ellipsis`를 사용한 가로 점 오버플로 메뉴를 둡니다. 오버플로 메뉴는 다음 순서로 구성합니다.

1. 파일 경로 변경, 복제
2. 문서 링크 복사, Git 파일 경로 복사, GitHub에서 보기
3. 구분선 아래의 `삭제 제안…`

확정 문서의 삭제는 즉시 실행하지 않고 삭제 변경 제안을 만듭니다. 위험 액션은 메뉴 마지막에 `Trash2` 아이콘과 danger 스타일로 표시하며, 대상 문서와 영향을 받는 링크를 설명하는 확인창을 거칩니다.

### Project

- 현재 단일 워크스페이스에 연결된 GitHub Project
- Project의 Board와 List
- 전체 Issue와 나에게 할당된 Issue
- Iteration, 사용자 정의 필드와 필터
- Issue 생성, 수정, 댓글과 종료
- 관련 기능·시나리오·처리 케이스·문서 표시
- 연결된 PR과 코드 확인

기본 정책은 `OKF 지식 저장소 1개 = 워크스페이스 1개 ↔ GitHub Project 1개`입니다. Project는 연결된 여러 저장소의 Issue와 PR을 모아 진행 상황을 보여주는 화면이고, 실제 구현 작업의 원본은 GitHub Issue입니다. 초기에는 추적 가능한 실제 Issue와 PR만 Project 항목으로 사용하고 Draft Issue 지원은 제외합니다.

작업 기간은 저장소별 GitHub Milestone이 아니라 GitHub Project의 `Iteration` 필드를 사용합니다. Project 화면은 현재 Iteration을 기본으로 보여주고 지난·다음 Iteration으로 전환할 수 있습니다.

Project 상단에는 프로젝트 이름과 Iteration 선택만 표시합니다. 진행률 요약은 Home의 책임으로 두고 Project에는 진행 막대, 퍼센트와 완료 개수를 중복 표시하지 않습니다. 별도 규칙이 없는 `On track`, `막힘`, `미할당` 요약도 표시하지 않습니다. 용도가 확정되지 않은 상단 더보기 메뉴와 전역 `새 Issue` 버튼도 두지 않습니다.

새 Issue는 현재 Iteration의 `Backlog` 컬럼 하단에서 생성합니다. 생성 UI는 기존 Issue와 같은 크기의 추가 카드이며, 카드 중앙에 `+ 새 Issue` 버튼을 표시합니다. 생성된 Issue는 `Backlog` 상태로 시작하며 이후 Board에서 다른 상태로 이동합니다. 다른 컬럼에는 반복적인 추가 버튼을 두지 않고, 종료된 지난 Iteration에서는 Issue를 추가하지 않습니다.

사용자 시나리오 전체 진행률은 Home에서 관련 문서 상태와 Project의 Issue를 조합해 보여줍니다. `Issues`를 별도 전역 메뉴로 중복 제공하지 않으며, Issue 상세는 Project 문맥 안에서 엽니다.

Board에서 Issue를 선택하면 우측 패널로 상세를 열어 빠르게 확인하고 처리합니다. 긴 본문, 문서, 코드나 diff를 넓게 봐야 할 때는 동일한 Issue를 전체 화면으로 확장할 수 있습니다.

Issue 상세 패널은 탭으로 내용을 숨기지 않고 다음 순서의 단일 스크롤로 구성합니다.

1. 저장소, Issue 번호, 제목, 상태와 담당자
2. 설명
3. 완료 조건 또는 체크리스트
4. 담당자, Iteration, Label과 저장소 속성
5. 연결된 문서, 코드와 PR
6. 댓글과 댓글 작성

우측 패널에서는 빠른 확인, 댓글과 상태 변경을 처리하고, 전체 화면으로 확장하면 같은 정보를 더 넓게 읽습니다. 상세 화면은 GitHub Issue의 개념과 동작을 새로 만들기보다 GitHub를 공유 원본으로 유지한 채 Hub 안에서 사용할 수 있게 옮겨 놓는 역할을 합니다. Hub만의 책임은 Issue와 문서·코드·PR·제품 구조의 연결을 한 문맥에서 보여주는 것입니다.

현재 승인한 것은 Issue 상세의 진입 방식과 정보 순서입니다. 시안에서 깨져 보이는 간격, 크기, 정렬과 반응형 표현은 최종 디자인 시스템 단계에서 다시 조정합니다.

### 문서 변경 제안·리뷰

문서 리뷰는 확정 문서를 직접 수정하지 않고 변경 제안 버전에서 진행합니다. 상단의 확인 범위는 다음 두 가지로 나눕니다.

- `제안 문서`: 변경이 모두 반영된 After 문서를 렌더링된 상태로 읽습니다. 리뷰 화면에서는 편집하지 않으므로 Markdown 원문 전환을 제공하지 않습니다.
- `변경 비교`: 확정본과 변경 제안의 차이를 확인합니다.
  - `줄 단위`: Git diff처럼 추가·삭제된 줄을 `+ / -`로 표시합니다.
  - `문서 비교`: 렌더링된 Before와 After 문서를 나란히 표시합니다.

우측 리뷰 패널은 확인 범위를 전환해도 유지하며 댓글, 선택형 결정, 승인과 수정 요청을 같은 변경 제안에 연결합니다.

리뷰 대상은 다음 수준으로 선택할 수 있습니다.

- 렌더링된 일반 문서: 드래그한 문장 또는 텍스트 범위
- 줄 단위 diff: 한 줄 또는 연속된 여러 줄
- Mermaid, 표와 코드: 초기에는 내부 요소가 아닌 블록 전체
- 선택하지 않은 경우: 문서 전체

텍스트를 드래그하거나 블록을 선택하면 가까운 위치에 `댓글`과 `결정 요청` 작업을 표시합니다. 문서 전체 의견은 우측 리뷰 패널의 추가 작업에서 작성합니다. 작성 패널에는 선택한 문구나 블록 이름을 인용해 어떤 부분에 연결되는지 명확히 보여줍니다.

댓글 연결 정보에는 제안 버전의 커밋, 문서 블록 식별자와 선택한 문구 또는 줄 범위를 포함합니다. 제안이 수정되어 대상을 다시 찾지 못하면 댓글을 없애지 않고 이전 버전에 달린 댓글로 표시합니다.

초기 `결정 요청`은 범용 설문 도구가 아니라 다음 범위만 제공합니다.

- 질문 1개
- 단일 선택
- 선택지 2~5개
- 선택 이유를 덧붙일 수 있는 선택적 의견
- 결정 확정과 종료

결정 요청과 각 응답은 연결된 GitHub PR의 구조화된 댓글로 공유하고, 승인·병합할 때 장기적으로 필요한 최종 결과를 OKF history 또는 문서 본문에 반영합니다.

Issue 또는 PR의 코드 리뷰에서는 코드 diff, 댓글, 승인과 수정 요청을 처리합니다. Home의 확인할 항목은 독립 리뷰 화면을 만들지 않고 해당 문서, Issue나 PR의 리뷰 문맥으로 이동합니다.

### API Catalog

OpenAPI를 원본으로 사용할 경우 Documents 안에 API 탐색 화면을 제공합니다.

- 서비스 또는 태그별 API 목록
- Path, method와 `operationId` 검색
- 요청·응답 스키마와 오류 계약
- 관련 기능과 처리 케이스
- 변경 제안과 버전 diff

API를 제품 구조 트리에 직접 중첩하지 않습니다.

## 공통 작업 화면

문서, 코드와 리뷰를 동시에 다루는 화면은 다음 영역을 조합할 수 있습니다.

```text
현재 문맥 탐색 | 문서 또는 리뷰 본문 | 관련 코드·API·변경 정보
```

- 좌측 영역은 항상 고정된 전체 트리가 아니라 현재 작업에 필요한 탐색을 제공합니다.
- 우측 보조 영역은 관련 코드, diff, 댓글 또는 속성으로 전환됩니다.
- 문서와 코드는 같은 화면에서 읽되 코드를 직접 편집하지 않습니다.

## 현재 UI 기술 후보

### 진행 순서

1. Home, Documents, Project, Settings와 문맥형 리뷰 화면의 정보 구성을 확정합니다.
2. 화면 간 이동과 주요 사용자 흐름을 확정합니다.
3. 전체 화면에서 반복되는 패턴을 기준으로 디자인 시스템을 확정합니다.
4. 확정된 디자인 시스템으로 고해상도 화면을 설계합니다.
5. 화면과 기술 명세가 승인된 뒤 구현 계획을 작성합니다.

화면 구성을 정하는 동안 만든 시안은 정보의 우선순위와 영역 배치를 검증하기 위한 것입니다. 시안의 개별 컴포넌트 모양을 최종 디자인으로 간주하지 않습니다.

### 합의된 방향

- Tauri + 웹 프론트엔드
- shadcn/ui 기반 컴포넌트
- 일반 화면은 여백이 있는 디자인, 트리·코드·테이블은 compact 밀도
- 문서 편집은 MDXEditor 계열 리치 에디터
- Markdown 원문과 diff는 CodeMirror
- 기본 서체는 `Pretendard Variable`을 사용하고 `Pretendard`와 시스템 sans-serif를 fallback으로 둡니다.
- 데스크톱 앱에 Pretendard 웹폰트 파일을 포함해 오프라인에서도 동일하게 렌더링합니다.
- 인터페이스 아이콘은 Lucide를 사용합니다.
- 의미가 불명확한 장식용 아이콘을 두지 않고, 아이콘 단독 버튼에는 이름 또는 tooltip을 제공합니다.
- 현재 시안의 중립 회색 surface, indigo primary와 상태별 green·amber·blue·red 색상 방향을 유지합니다.

이전에 사용한 `Nova`는 디자인 스타일 후보 이름이며 프로젝트명이 아닙니다.

Home 시안 우측 상단의 클로버 모양은 기능이 정해지지 않은 임시 표시였으므로 제거합니다. 우측 상단에는 현재 동기화와 사용자 메뉴만 두고, 실제 전역 기능이 확정될 때만 아이콘을 추가합니다.

### 미결정

- Documents의 Library·Structure·History·APIs 하위 탐색 방식
- 제품 구조 트리를 항상 표시할지 필요할 때만 표시할지
- Home의 확인할 항목에서 문서·Issue·PR 화면으로 전환하는 방식
- Project의 Board·List·My Issues·Iterations 하위 탐색 방식
- 정확한 색상·타이포그래피·간격 토큰과 컴포넌트 variant
- Lucide 아이콘별 제품 의미와 기본 크기·stroke 규칙
