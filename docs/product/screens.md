# 화면 구성

이 문서는 합의된 전역 화면 구조와 아직 구체화 중인 화면별 책임을 정리합니다.

앱 화면의 짧은 브랜드 표기는 `OkHub`를 사용합니다. Git 저장소와 프로젝트의 정식 이름 `okf-knowledge-hub`는 바꾸지 않습니다. 색상, 타이포그래피와 공통 컴포넌트 기준은 [디자인 시스템](design-system.md)을 따릅니다.

## 앱 수준 화면

### 최초 연결 화면

워크스페이스가 연결되지 않은 최초 실행 또는 연결 복구가 필요할 때만 표시합니다.

- `GitHub 로그인 → OKF 저장소 선택 → 로컬 연결`의 3단계 화면을 사용합니다.
- 한 단계에서 한 가지 결정만 처리하고, 상단 단계 표시로 현재 위치와 완료 상태를 보여줍니다.
- GitHub 로그인은 GitHub App의 Device Flow를 사용하고 인증 정보는 OS 보안 저장소에 보관합니다.
- 저장소 선택 단계에서는 사용자와 OkHub GitHub App이 모두 접근할 수 있는 기존 OKF 지식 저장소만 설치 계정·조직별로 보여줍니다. Hub가 GitHub 저장소 자체를 만들지는 않으며, 원하는 저장소가 없으면 `GitHub에서 새 저장소 만들기`와 `GitHub App 저장소 권한 관리`를 별도 행동으로 제공합니다. 사용자가 Hub로 돌아오면 목록을 자동으로 다시 확인하고 수동 새로고침은 보조 기능으로만 둡니다.
- 로컬 연결 단계에서는 기존 clone 폴더를 선택하거나 새 로컬 위치를 골라 Hub가 clone하도록 합니다.
- `.okf/workspace.yml`이 있으면 설정을 검증하고, 없으면 생성될 파일과 대상 저장소를 먼저 보여준 뒤 워크스페이스 초기화를 실행합니다.
- 완전히 빈 저장소는 기본 브랜치에 초기 커밋을 push하고, 기존 파일이 있는 저장소는 `okf/init-workspace` 브랜치와 Draft PR로 초기화를 제안합니다.
- `워크스페이스 초기화` 클릭은 화면에 고지된 파일의 commit과 push에 대한 명시적 승인으로 취급합니다. 실패하면 로컬 결과를 보존하고 원인을 보여줍니다.

최근 워크스페이스 목록, 워크스페이스 선택과 전환 화면은 제공하지 않습니다. 연결이 완료된 뒤 앱을 다시 열면 현재 워크스페이스의 Home으로 바로 진입합니다.

### 워크스페이스 설정

Settings는 사용 목적을 기준으로 다음 여섯 영역으로 나눕니다.

1. `워크스페이스`
   - 현재 OKF 지식 저장소와 로컬 clone 경로
   - `.okf/workspace.yml` 검증과 동기화 상태
   - 현재 연결을 다른 OKF 저장소로 교체
2. `외부 연결`
   - GitHub 인증과 계정 관리
   - 백엔드·프론트엔드 등 여러 코드 저장소
   - 워크스페이스에 연결할 GitHub Project 하나
3. `문서`
   - 문서 루트 경로
   - 앱 내장 기본 템플릿 조회
   - `.okf/templates/`의 워크스페이스 템플릿 관리
4. `작업 방식`
   - 기본 브랜치와 worktree 위치
   - Issue Assignee 기반 문서 편집 잠금
   - 로컬 체크포인트와 온라인 복구 규칙
5. `화면`
   - 기기별 표시 밀도 `Default`와 `Compact`
   - 기본값은 `Default`
   - 선택은 로컬 설정에만 저장하며 Git으로 공유하지 않음
6. `AI 연동`
   - 로컬 MCP 서버 상태와 설정 안내
   - AI 도구에 허용할 읽기·쓰기·상태 변경 범위
   - Codex 등 외부 AI 도구에 붙여 넣을 MCP 설정

Settings 안에는 별도의 보조 탐색을 두고 위 여섯 영역을 세로 목록으로 표시합니다. `워크스페이스`는 필수, `AI 연동`은 선택 사항임을 표시합니다. 화면 상단에는 필수 연결의 전체 상태를 간단히 보여주되 동기화 작업을 위한 별도 전역 헤더는 만들지 않습니다.

다른 OKF 저장소로 바꾸면 최초 연결의 3단계 흐름으로 이동합니다. 이 동작은 앱이 바라보는 현재 연결만 교체하며 기존 로컬 폴더를 자동으로 삭제하지 않습니다.

프로젝트 저장소 연결은 워크스페이스의 좌측 주 메뉴에 두지 않습니다. Settings는 현재 단일 워크스페이스의 연결을 관리하며 다른 워크스페이스로 빠르게 전환하는 선택기를 제공하지 않습니다.

## 워크스페이스 전역 구조

**상태: 합의**

```text
Home
Documents
Project
────────
Settings
```

- `Work`는 독자적인 데이터와 행동이 없어 전역 메뉴에서 제외합니다.
- `Activity`는 Home의 타임라인으로 흡수합니다.
- `Reviews`는 독립 콘텐츠가 아니라 문서나 PR에 붙는 처리 과정이므로 전역 메뉴에서 제외합니다.
- 사용자가 확인해야 할 검토, 결정과 작업 시작 알림은 Home에서 모아 보여주고, 실제 처리는 원래 문서, Issue나 PR 문맥에서 진행합니다.
- 사이드바 상단에는 현재 프로젝트 이름을 정적인 식별 정보로 표시하며 드롭다운 화살표나 워크스페이스 선택 동작을 두지 않습니다.
- 좌측 사이드바는 완전히 접을 수 있으며, 접으면 본문이 남은 폭을 사용합니다. 펼친 상태의 토글은 사이드바 최상단 오른쪽에 두고, 접힌 상태에서는 같은 기능의 버튼을 본문 왼쪽 위에 표시합니다.
- 사이드바 토글은 Lucide의 `PanelLeftClose`·`PanelLeftOpen` 계열 아이콘과 설명 tooltip을 사용하고, macOS `Command + Backslash`, Windows `Ctrl + Backslash` 단축키를 제공합니다.

### Home

앱을 열었을 때 현재 단일 워크스페이스의 프로젝트 진행 상황과 다음 행동을 보여줍니다.

- `프로젝트 진행 상황` 제목
- 제목 아래의 인사말과 오늘 날짜
- 열린 Issue, 진행 중인 Issue, 이번 주 완료 Issue 요약
- 기능별 진행률과 완료 Issue 수
- 내가 확인할 항목
  - 검토 필요
  - 결정 필요
  - 작업 시작 가능
  - 응답 필요
- 발생 시간을 포함한 최근 활동

기능 진행률은 초기에는 연결된 Issue의 `완료 수 / 전체 수`로 계산하고 퍼센트와 실제 개수를 함께 보여줍니다. 작업 크기를 반영한 가중 진행률은 초기 범위에서 제외합니다.

백엔드 API 완료처럼 누군가의 승인이 필요하지 않더라도 후속 작업자가 다음 행동을 시작해야 하는 이벤트는 `작업 시작 가능` 항목으로 표시합니다. 연결된 선행 Issue 종료나 PR 병합을 기준으로 만들며, 정확한 연결이 없으면 자동으로 추론하지 않습니다.

Home의 정보 구성, 표시 순서와 영역별 책임을 확정했습니다. 색상, 타이포그래피, 간격과 카드 표현은 [디자인 시스템](design-system.md)을 따릅니다.

### Documents

- 제품 구조 탐색
- 문서 라이브러리
- 문서 편집과 렌더링
- 문서별 Git history
- 관련 분석·테스트·API·코드
- 현재 버전과 제안 버전 전환

Documents는 문서가 중심인 공간입니다. `History`는 별도 전역 메뉴가 아니라 각 문서의 커밋·변경·승인 이력을 보여주는 상세 보기입니다. 진행 중인 작업을 별도 목록으로 소유하지 않으며, 문서에서 관련 Issue나 리뷰 상태를 참조 정보로 확인할 수 있습니다.

초기 Documents 탐색은 `.okf/workspace.yml`에 설정된 문서 루트 아래의 Markdown 파일만 대상으로 합니다. 제목은 `frontmatter.title`을 우선하고 없으면 파일명을 사용하며, 첫 번째 H1은 본문으로 취급합니다. frontmatter가 없거나 잘못되어도 문서를 숨기지 않고 속성 영역에 경고를 표시합니다.

문서 트리는 본문 전체 색인을 기다리지 않고 먼저 표시합니다. 제목·경로·본문 검색에는 워크스페이스별 로컬 검색 캐시를 사용하며, 최초 색인 중에는 제목과 경로 검색을 먼저 제공하고 `본문 검색을 준비하는 중…` 상태를 표시합니다. 검색 결과에는 제목, 경로와 검색어 주변 본문을 보여주고 선택하면 첫 번째 일치 위치로 이동합니다.

문서 상세는 기본적으로 읽기 모드로 엽니다. 기본 브랜치의 확정 문서에서 `편집`을 누르면 변경 제안을 만들고, 이미 작업 브랜치나 PR 버전을 보고 있다면 해당 버전을 바로 편집합니다.

상세 화면은 다음 3개 영역을 사용합니다.

```text
문서 트리 | 읽기·리치 편집·Markdown 원문 캔버스 | 접을 수 있는 문맥 패널
```

- 본문 캔버스는 한 번에 읽기, 리치 편집 또는 원문 중 하나에 집중합니다.
- 우측 문맥 패널은 `개요 / 연결 / History / 댓글` 탭으로 구성합니다.
- `개요`는 문서 속성을 먼저 보여주고 그 아래에 목차를 표시합니다.
- `연결`에는 관련 Issue, PR, 코드와 API를 모아 보여줍니다.
- `댓글`은 변경 제안이나 리뷰 문맥에서만 표시합니다.
- 문서 제목 아래에는 `확정본 · main`과 같이 현재 Git 버전을 보여주는 선택기를 둡니다. 초기 읽기 단계에서는 현재 작업 트리와 commit 이력만 제공하고, 열린 변경 제안과 개수 배지는 리뷰 기능 단계에서 연결합니다.
- 마지막 수정 시각과 작성자는 제목 아래에 짧게 표시하고, 커밋별 상세 수정 이력과 diff는 우측 `History` 탭에서 확인합니다.

문서 제목과 Git 파일 경로는 서로 다른 값으로 다룹니다. 화면에 보이는 제목은 OKF frontmatter의 `title`이며 편집 모드에서 수정합니다. 파일명과 폴더를 바꾸는 구조 작업은 오버플로 메뉴의 `파일 경로 변경…`으로 제공하고, 영향받는 문서 링크를 확인한 뒤 변경 제안에 반영합니다. 의미가 모호한 `이름 변경` 액션은 사용하지 않습니다.

문서 헤더의 주요 작업은 텍스트 `편집` 버튼으로 노출하고, 그 옆에 Lucide `Ellipsis`를 사용한 가로 점 오버플로 메뉴를 둡니다. 오버플로 메뉴는 다음 순서로 구성합니다.

1. 파일 경로 변경, 복제
2. 문서 링크 복사, Git 파일 경로 복사, GitHub에서 보기
3. 구분선 아래의 `삭제 제안…`

확정 문서의 삭제는 즉시 실행하지 않고 삭제 변경 제안을 만듭니다. 위험 액션은 메뉴 마지막에 `Trash2` 아이콘과 danger 스타일로 표시하며, 대상 문서와 영향을 받는 링크를 설명하는 확인창을 거칩니다.

#### 새 문서 생성

Documents 상단의 `+ 새 문서`와 좌측 문서 트리의 `+ → 새 문서`는 같은 생성창을 엽니다. 상단 버튼은 마지막으로 사용한 문서 폴더를, 트리의 버튼은 사용자가 선택한 폴더를 기본 저장 위치로 채웁니다. Documents 루트에서 실행하면 문서 루트를 선택합니다.

생성창은 다음 정보만 받습니다.

1. 필수 문서 제목
2. 제목으로 자동 생성되며 생성 전에 수정할 수 있는 Git 파일 이름
3. 필수 저장 위치
4. 기본값이 `빈 문서`인 템플릿

파일 이름은 한글을 포함한 읽을 수 있는 형태로 생성하고 Git에서 사용할 수 없는 문자를 정리합니다. 같은 경로가 이미 있으면 자동으로 번호를 붙이지 않고 충돌을 알린 뒤 사용자가 경로나 파일 이름을 바꾸게 합니다.

템플릿 선택기는 검색 없이 현재 선택 항목과 펼쳐지는 목록이 연결된 단일 select 형태를 사용합니다. 현재 선택 항목은 강조 배경과 Lucide `Check` 아이콘으로 표시하며, 목록은 다음 9개 기본 템플릿을 그룹별로 제공합니다.

```text
빈 문서

설계
├─ 기능·처리 흐름 설계
├─ API·DTO 설계
└─ 기술 결정 기록

조사·검증
├─ 기술 조사
├─ 실험·성능 분석
└─ 테스트 계획·결과

운영
├─ 운영 가이드·Runbook
└─ 장애 회고
```

워크스페이스 템플릿이 있으면 기본 템플릿 아래에 `워크스페이스` 그룹으로 이어서 표시합니다. 항목 수가 메뉴 높이를 넘으면 목록 내부만 스크롤하며 별도 검색 필드는 제공하지 않습니다.

문서를 만들면 Hub가 문서 ID와 초안 작업 공간을 준비하고 선택한 템플릿 본문을 채운 뒤 리치 편집 화면을 바로 엽니다. 템플릿은 수정 가능한 시작점이며, 생성된 문서를 이후 템플릿 변경과 자동 동기화하지 않습니다.

### Project

- 현재 단일 워크스페이스에 연결된 GitHub Project
- Project의 Board와 List
- 전체 Issue와 나에게 할당된 Issue
- Iteration, 사용자 정의 필드와 필터
- Issue 생성, 수정, 댓글과 종료
- 관련 기능·시나리오·처리 케이스·문서 표시
- 연결된 PR과 코드 확인

기본 정책은 `OKF 지식 저장소 1개 = 워크스페이스 1개 ↔ GitHub Project 1개`입니다. Project는 연결된 여러 저장소의 Issue와 PR을 모아 진행 상황을 보여주는 화면이고, 실제 구현 작업의 원본은 GitHub Issue입니다. 초기에는 추적 가능한 실제 Issue와 PR만 Project 항목으로 사용하고 Draft Issue 지원은 제외합니다.

작업 기간은 저장소별 GitHub Milestone이 아니라 GitHub Project의 `Iteration` 필드를 사용합니다. Project 화면은 현재 Iteration을 기본으로 보여주고 지난·다음 Iteration으로 전환할 수 있습니다.

Project 상단에는 프로젝트 이름과 Iteration 선택만 표시합니다. 진행률 요약은 Home의 책임으로 두고 Project에는 진행 막대, 퍼센트와 완료 개수를 중복 표시하지 않습니다. 별도 규칙이 없는 `On track`, `막힘`, `미할당` 요약도 표시하지 않습니다. 용도가 확정되지 않은 상단 더보기 메뉴와 전역 `새 Issue` 버튼도 두지 않습니다.

새 Issue는 현재 Iteration의 `Backlog` 컬럼 하단에서 생성합니다. 생성 UI는 기존 Issue와 같은 크기의 추가 카드이며, 카드 중앙에 `+ 새 Issue` 버튼을 표시합니다. 생성된 Issue는 `Backlog` 상태로 시작하며 이후 Board에서 다른 상태로 이동합니다. 다른 컬럼에는 반복적인 추가 버튼을 두지 않고, 종료된 지난 Iteration에서는 Issue를 추가하지 않습니다.

사용자 시나리오 전체 진행률은 Home에서 관련 문서 상태와 Project의 Issue를 조합해 보여줍니다. `Issues`를 별도 전역 메뉴로 중복 제공하지 않으며, Issue 상세는 Project 문맥 안에서 엽니다.

Board에서 Issue를 선택하면 우측 패널로 상세를 열어 빠르게 확인하고 처리합니다. 긴 본문, 문서, 코드나 diff를 넓게 봐야 할 때는 동일한 Issue를 전체 화면으로 확장할 수 있습니다.

Issue 상세 패널은 탭으로 내용을 숨기지 않고 다음 순서의 단일 스크롤로 구성합니다.

1. 저장소, Issue 번호, 제목, 상태와 담당자
2. 설명
3. 완료 조건 또는 체크리스트
4. 담당자, Iteration, Label과 저장소 속성
5. 연결된 문서, 코드와 PR
6. 댓글과 댓글 작성

우측 패널에서는 빠른 확인, 댓글과 상태 변경을 처리하고, 전체 화면으로 확장하면 같은 정보를 더 넓게 읽습니다. 상세 화면은 GitHub Issue의 개념과 동작을 새로 만들기보다 GitHub를 공유 원본으로 유지한 채 Hub 안에서 사용할 수 있게 옮겨 놓는 역할을 합니다. Hub만의 책임은 Issue와 문서·코드·PR·제품 구조의 연결을 한 문맥에서 보여주는 것입니다. 간격, 크기, 정렬과 상태 표현은 [디자인 시스템](design-system.md)을 따릅니다.

현재 승인한 것은 Issue 상세의 진입 방식과 정보 순서입니다. 시안에서 깨져 보이는 간격, 크기, 정렬과 반응형 표현은 최종 디자인 시스템 단계에서 다시 조정합니다.

### 문서 변경 제안·리뷰

문서 리뷰는 확정 문서를 직접 수정하지 않고 변경 제안 버전에서 진행합니다. 상단의 확인 범위는 다음 두 가지로 나눕니다.

- `제안 문서`: 변경이 모두 반영된 After 문서를 렌더링된 상태로 읽습니다. 리뷰 화면에서는 편집하지 않으므로 Markdown 원문 전환을 제공하지 않습니다.
- `변경 비교`: 확정본과 변경 제안의 차이를 확인합니다.
  - `줄 단위`: Git diff처럼 추가·삭제된 줄을 `+ / -`로 표시합니다.
  - `문서 비교`: 렌더링된 Before와 After 문서를 나란히 표시합니다.

우측 리뷰 패널은 확인 범위를 전환해도 유지하며 댓글, 선택형 결정, 승인과 수정 요청을 같은 변경 제안에 연결합니다.

리뷰 대상은 다음 수준으로 선택할 수 있습니다.

- 렌더링된 일반 문서: 드래그한 문장 또는 텍스트 범위
- 줄 단위 diff: 한 줄 또는 연속된 여러 줄
- Mermaid, 표와 코드: 초기에는 내부 요소가 아닌 블록 전체
- 선택하지 않은 경우: 문서 전체

텍스트를 드래그하거나 블록을 선택하면 가까운 위치에 `댓글`과 `결정 요청` 작업을 표시합니다. 문서 전체 의견은 우측 리뷰 패널의 추가 작업에서 작성합니다. 작성 패널에는 선택한 문구나 블록 이름을 인용해 어떤 부분에 연결되는지 명확히 보여줍니다.

댓글 연결 정보에는 제안 버전의 커밋, 문서 블록 식별자와 선택한 문구 또는 줄 범위를 포함합니다. 제안이 수정되어 대상을 다시 찾지 못하면 댓글을 없애지 않고 이전 버전에 달린 댓글로 표시합니다.

초기 `결정 요청`은 범용 설문 도구가 아니라 다음 범위만 제공합니다.

- 질문 1개
- 단일 선택
- 선택지 2~5개
- 선택 이유를 덧붙일 수 있는 선택적 의견
- 결정 확정과 종료

결정 요청과 각 응답은 연결된 GitHub PR의 구조화된 댓글로 공유하고, 승인·병합할 때 장기적으로 필요한 최종 결과를 OKF history 또는 문서 본문에 반영합니다.

Issue 또는 PR의 코드 리뷰에서는 코드 diff, 댓글, 승인과 수정 요청을 처리합니다. Home의 확인할 항목은 독립 리뷰 화면을 만들지 않고 해당 문서, Issue나 PR의 리뷰 문맥으로 이동합니다.

### API Catalog

OpenAPI를 원본으로 사용할 경우 Documents 안에 API 탐색 화면을 제공합니다.

- 서비스 또는 태그별 API 목록
- Path, method와 `operationId` 검색
- 요청·응답 스키마와 오류 계약
- 관련 기능과 처리 케이스
- 변경 제안과 버전 diff

API를 제품 구조 트리에 직접 중첩하지 않습니다.

## 공통 작업 화면

문서, 코드와 리뷰를 동시에 다루는 화면은 다음 영역을 조합할 수 있습니다.

```text
현재 문맥 탐색 | 문서 또는 리뷰 본문 | 관련 코드·API·변경 정보
```

- 좌측 영역은 항상 고정된 전체 트리가 아니라 현재 작업에 필요한 탐색을 제공합니다.
- 우측 보조 영역은 관련 코드, diff, 댓글 또는 속성으로 전환됩니다.
- 문서와 코드는 같은 화면에서 읽되 코드를 직접 편집하지 않습니다.

## UI 기술과 디자인 시스템

### 진행 순서

1. Home, Documents, Project, Settings와 문맥형 리뷰 화면의 정보 구성을 확정했습니다.
2. 화면 간 이동과 주요 사용자 흐름을 확정했습니다.
3. 전체 화면에서 반복되는 패턴을 기준으로 [디자인 시스템](design-system.md)을 확정했습니다.
4. 구현 중 필요한 고해상도 화면은 승인된 정보 구조와 디자인 시스템을 기준으로 작성합니다.
5. 남은 제품·기술 명세를 승인한 뒤 구현 계획을 작성합니다.

화면 구성을 정하는 동안 만든 시안은 정보의 우선순위와 영역 배치를 검증하기 위한 것입니다. 시안의 개별 컴포넌트 모양을 최종 디자인으로 간주하지 않습니다.

### 합의된 방향

- Tauri + 웹 프론트엔드
- shadcn/ui primitive와 OkHub 제품 pattern을 분리한 컴포넌트 구조
- 탐색·Board·Settings는 compact하게, 문서 본문·편집·리뷰는 편안하게 표시하는 Adaptive 밀도
- 문서 읽기는 `react-markdown`, 리치 편집은 `MDXEditor`, Markdown 원문과 줄 단위 diff는 `CodeMirror`를 사용합니다.
- 기본 서체는 `Pretendard Variable`을 사용하고 `Pretendard`와 시스템 sans-serif를 fallback으로 둡니다.
- 데스크톱 앱에 Pretendard 웹폰트 파일을 포함해 오프라인에서도 동일하게 렌더링합니다.
- 인터페이스 아이콘은 Lucide를 사용합니다.
- 의미가 불명확한 장식용 아이콘을 두지 않고, 아이콘 단독 버튼에는 이름 또는 tooltip을 제공합니다.
- 중립 회색 surface와 Aqua Mint `#009E8E` Primary를 사용하고, 상태별 green·blue·amber·red는 고정된 Semantic 의미에만 사용합니다.

### 문서 렌더링과 편집

- Git에 저장되는 OKF Markdown을 유일한 문서 원본으로 유지하고 편집기 전용 JSON이나 HTML을 별도 원본으로 저장하지 않습니다.
- 읽기 화면은 편집기와 분리해 `react-markdown`과 remark 계열 플러그인으로 렌더링합니다.
- 리치 편집 엔진은 Markdown 문자열을 입력·출력하는 `MDXEditor`를 사용합니다. 기본 외형은 그대로 사용하지 않고 shadcn/ui, Lucide와 제품 디자인 토큰으로 BlockNote처럼 간결한 블록형 작성 경험을 구성합니다.
- Markdown 원문과 줄 단위 diff에는 `CodeMirror`를 사용합니다. 리치 편집이 지원하지 않는 문법을 발견하면 내용을 변환하거나 제거하지 않고 원문 모드로 안내합니다.
- OKF frontmatter는 본문 편집 영역과 분리해 우측 문서 속성 패널에서 다룹니다. 명시적으로 속성을 수정하지 않은 경우 원본 frontmatter를 다시 직렬화하지 않습니다.
- `mermaid` fenced code block은 원문을 보존하면서 편집 화면에서는 전용 코드 블록과 다이어그램 미리보기를 제공합니다.
- 단순히 문서를 열고 닫은 경우 파일을 다시 쓰지 않습니다. 실제 편집 시에도 지원 문법에 대한 Markdown 왕복 변환 테스트로 frontmatter, 표, 중첩 목록, 코드 블록 metadata, Mermaid와 링크가 보존되는지 검증합니다.

BlockNote는 시각적·상호작용 참고 대상으로만 사용합니다. 기본 Markdown import/export가 손실 가능하므로 편집 엔진으로 사용하지 않습니다. Milkdown은 Markdown 중심의 확장성은 좋지만 초기 제품에서 frontmatter, 원문 전환, Mermaid와 리뷰 기능을 추가 조립해야 하는 범위가 더 커 우선 선택하지 않습니다.

이전에 사용한 `Nova`는 디자인 스타일 후보 이름이며 프로젝트명이 아닙니다.

Home 시안 우측 상단의 클로버 모양은 기능이 정해지지 않은 임시 표시였으므로 제거합니다. 별도의 전역 동기화 header를 만들지 않고 Settings를 좌측 주 메뉴에, 사용자 정보는 사이드바 하단에 둡니다. 실제 전역 기능이 확정될 때만 아이콘을 추가합니다.

### 미결정

- Documents의 Library·Structure·History·APIs 하위 탐색 방식
- 제품 구조 트리를 항상 표시할지 필요할 때만 표시할지
- Home의 확인할 항목에서 문서·Issue·PR 화면으로 전환하는 방식
- Project의 Board·List·My Issues·Iterations 하위 탐색 방식
